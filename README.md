# BiddingAnalysis

盘前竞价系统

**在线地址：https://aimi-ding.github.io/BiddingAnalysis/**

> 竞价分析系统（修复版）：基于东方财富公开行情接口的 A 股集合竞价选股看板。
> 本项目在原版基础上修正了四处计算错误，并更正了若干没有依据的指标名称。

---

A股集合竞价时段的选股看板。左右两栏各自按一套规则筛股、打分、排序，可导出到通达信/大智慧。

**这个项目基于一份现成的单文件 HTML 改写**，主要工作是修正原版里几处算错的逻辑，并把没有依据的指标名改回它真正的含义。

- 主文件：`index.html`（单文件，双击即可用，无需安装）
- 数据源：东方财富公开行情接口
- 验证脚本：`verify/`（需要 Node 和本机 Chrome）

---

## 一、数据从哪来，是否可信

只连一个接口：

```
https://push2dycalc.eastmoney.com/api/qt/clist/get
```

**是真数据。** 核实方式：

1. 域名 HTTPS 证书签发给 `O=East Money Information Co., Ltd.`，属东方财富自己
2. 与腾讯、新浪行情交叉核对，同一时刻同一只股票完全一致
3. 不需要注册、不需要 key、不需要登录，去掉请求里那个 `ut=` 参数照样返回

**也是免费的**，但要知道它的性质：

- 它是东财**网页前端自用的内部接口**，不是对外文档化的 API
- 没有服务条款、没有可用性承诺、字段可能变、高频访问可能被限流
- 自己看没问题；要做成对外产品需自行评估

### 字段含义（实测自接口返回）

| 字段 | 含义 | 字段 | 含义 |
|---|---|---|---|
| f2 | 最新价 | f12 | 代码 |
| f3 | 涨跌幅 % | f14 | 名称 |
| f4 | 涨跌额 | f18 | 昨收价 |
| f5 | 成交量（手） | f20 | 总市值（元） |
| f6 | 成交额（元） | f21 | 流通市值（元） |
| f10 | 量比 | f615 | 竞价涨幅 % |
| f630 | 警示类型 | f100/f102/f103 | 行业/省份/概念 |

### 一个必须知道的时间限制

`f615`（竞价涨幅）**只在 9:15–9:25 集合竞价时段有效**，开盘后就不再更新。所以这个看板只有早上竞价那段时间打开才有意义，其他时候看到的是冻结值。

## 二、修复了什么

### 修复 ①：左侧「成交额」一项永远是 0

原代码：

```js
const amount = stock.f20 || 0;          // 读 f20
```

但请求的 `fields` 里根本没有 `f20`，取到的是 `undefined`：

```
f2,f3,f4,f5,f10,f12,f14,f615,f630,f100,f102,f103     ← 无 f20
```

于是 `log10(0+1)/9 = 0`，这一项 12% 的权重永远拿不到分，左侧总分理论上限只有 88 分。

改法：改用 **f6 成交额**，并把 f6/f18/f20/f21 补进请求字段。

为什么不按原名用 f20（总市值）？实测对比：

| 用哪个字段 | 该项满分比例 | 有区分度吗 |
|---|---|---|
| f20 总市值 | 97 / 100 只满分 | 几乎等于白送 |
| f6 成交额 | 12 / 100 只满分 | 能拉开差距 |

`log10(x)/9` 这个设计本身就是给「10 亿成交额即满分」准备的，所以用成交额才对。

实测效果：东方海洋成交额 13 亿，该项从 0 分变 12 分；整体最高分从 65 → 77。

### 修复 ②：「剔除昨日涨停」这条规则完全没生效

原代码：

```js
function getYesterdayChange(stock) {
    let current = stock.f4 || 0;    // f4 是"涨跌额"
    let prev    = stock.f2 || 0;    // f2 是"最新价"
    return ((current - prev) / prev) * 100;
}
```

它把「涨跌额」当成「昨日收盘价」去算。实测三只股票：

```
易天股份   算出 -83.33%   实际 +20.00%
*ST仕净    算出 -86.49%   实际 +15.63%
满坤科技   算出 -87.25%   实际 +14.61%
```

恒为大负数，而判断条件是 `>= 9.5 就剔除`——**永远不成立**。

而且这里有个更根本的问题：**接口不提供「前日收盘价」，所以「昨日涨幅」在数学上算不出来。**

改法：用东财自己在概念字段里标的「昨日涨停 / 昨日首板」标签判断。它和 `f4/f2` 无关，是交易所口径的事实标签。

把 `getYesterdayChange` 正名为 `getTodayChange`（相对昨收的今日涨幅），并新增 `isYesterdayLimitUp`。

实测效果：某一时刻涨幅前 100 里有 8 只概念含「昨日涨停/首板」的股票，**改前漏掉 4 只（中京电子、真视通、襄阳轴承、金科股份），改后 0 只**。

### 修复 ③：把「量比」当成「流通市值」用

原代码：

```js
const circulationMarketValue = stock.f10 || 0;    // f10 是量比
```

真实流通市值是 `f21`。两者差几个数量级：

```
易天股份   f10=15.36(量比)   f21=32.03亿(真实流通市值)
*ST仕净    f10=7.25          f21=6.73亿
满坤科技   f10=5.53          f21=46.21亿
```

原算法 `成交量 / (流通市值/10000)` 用 f10 算出来是上亿的量级，必然命中最高档拿满分，这一项等于没做。

改法：改用 f21，并把算法换成有明确含义的**竞价换手率**：

```
流通股本  = 流通市值 / 现价
竞价换手率 = 竞价成交量(股) / 流通股本 × 100%
```

实测校验：易天股份算得 **11.92%**，腾讯行情同时刻给的是 **11.88%**（差异来自快照时间差几秒），量纲正确。

### 修复 ④：右侧权重加起来只有 0.95

```js
relativeVolumeScore*0.3 + warnScore*0.2 + bidChangeScore*0.2 + yestScore*0.15 + mvScore*0.10
```

`0.30+0.20+0.20+0.15+0.10 = 0.95`，不足 1，导致右侧分数天然比左侧低 5 分，两栏不能横向比较。

改法：按原相对比例归一化（整体除以 0.95），相对权重一点没动，只是把总分拉回 0–100。

实测效果：右侧分数区间从 51–74 变成 37–86，区分度明显拉开。

## 三、附带修的三处

这三处不在最初列的四项里，但属于同一类问题，一并处理了。

### 1. 「涨停率」与「AI 智能研判」是虚假指标名

界面写着「涨停率 87%」「涨停率基于 AI 多维模型」「AI 智能研判」，但代码里：

- **没有任何模型参与**，没有调用、没有训练、没有回测
- 那个百分比就是 6 个指标的手工加权求和
- 「可信度 70%~96%」是 `70 + 两个归一化值`，没有统计含义

改法：

| 原显示 | 改为 | 理由 |
|---|---|---|
| 涨停率 87% | 综合分 87 | 不是概率 |
| 可信度 82% | 数据完整度 82% | 如实统计本次打分有几个因子拿到了真实数据 |
| AI 智能研判 | 规则打分 | 没有 AI |
| 涨停率基于 AI 多维模型 | 综合分为指标加权评分，非涨停概率预测 | 同上 |

**这一条是性质问题，不是措辞问题。** 把加权分说成「涨停概率」，对外使用时属于虚标。

### 2. 表格「涨速」列显示的是量比

原代码 `<th>涨速</th>` 但取 `speed: s.f10`，而 f10 是量比，涨速是 f22。

改法：表头改为「量比」，与字段一致（量比本身在竞价分析里比涨速有用）。

### 3. 图标全部加载失败

CSP 里放行了 `style-src cdnjs.cloudflare.com`，但没有 `font-src`，Font Awesome 的字体文件被 `default-src` 拦掉，垃圾桶、下载、刷新这些图标全是空白。

改法：补 `font-src 'self' data: https://cdnjs.cloudflare.com;`，并清掉 `default-src` 里那几个无效 token（`'unsafe-inline' 'unsafe-eval'` 只对 `script-src` 有效）。

修完浏览器控制台不再报字体错误。

## 四、怎么用

直接双击 `index.html`，或者起个本地服务（推荐，避免 `file://` 的跨域限制）：

```bash
cd auction-screener
python3 -m http.server 8899
# 打开 http://127.0.0.1:8899/index.html
```

**或者直接用在线版：https://aimi-ding.github.io/BiddingAnalysis/**（免安装，功能一致）

**最佳使用时间：交易日 9:15–9:25。** 9:30 之后 `f615` 已冻结，看板的排序依据就失效了。

> 注意：本仓库为公开仓库，GitHub Pages 站点本身也是公开可访问的。如果不希望别人打开这个页面，请自己本地跑。

### 导出与联动

- 「导出至通达信」会跳 `http://www.treeid/AddToBlock_...`，这是通达信在本机注册的处理程序，靠 HTTP 请求唤起客户端
- 「联动：大智慧」用 `dzh://VIEWSTOCK?PAGE=技术分析&LABEL=代码`

两者都依赖本机装了对应软件。这是非官方的协议唤起方式，软件升级后可能失效。

## 五、怎么验证

### 1. 浏览器端到端

```bash
# 在项目上级目录执行（该目录需已安装 puppeteer-core + 本机有 Chrome）
node auction-screener/verify/e2e.mjs
```

预期：`pageerror` 和 `consoleError` 均为空（除 favicon 404），卡片和表格正常渲染，所有分数在 0–100 之间。

需要先在 8899 起静态服务，脚本里 URL 是 `http://127.0.0.1:8899/index.html`。

### 2. 新旧算法对比

```bash
node auction-screener/verify/compare.mjs
```

这个脚本会用同一批实时行情，分别跑「改前」和「改后」两套逻辑，输出：

- 昨日涨停股漏网数量（改前 vs 改后）
- 通过筛选的数量
- 左侧前三、右侧前五的名单差异
- 分数区间变化
- 竞价换手率与腾讯行情的交叉校验

**注意：** 脚本每跑一次数据都不同（实时行情在变），因此具体名单会变，但「改前漏网 > 0、改后 = 0」这个结论是稳定的。

### 3. 快照记录器

```bash
node auction-screener/verify/snapshot.mjs
```

会清空已有的 IndexedDB、点一次「立即抓取」、再读回来核对。预期：

```json
{
  "afterCount": 1,
  "record": { "date": "2026-11-20", "quality": 0, "count": 5005, ... }
}
```

`count` 应在 4000–5500 之间（全市场去掉 ST/停牌/一字板）。如果抓到个位数，说明接口或字段变了。

**这个脚本还会校验字段正确性**——`f17`（今开）和 `f615`（竞价涨幅）必须自洽，即 `(f17/f18-1)*100 ≈ f615`。实测 5005 条里 4988 条吻合（99.66%），不吻合的多是除权日。

## 六、积累真实竞价数据（为后续回测）

回测卡在一个数据瓶颈上：**东方财富没有历史「竞价快照」接口**。竞价量、量比这些字段只有实时值，事后拿不到。

所以看板内置了一个记录器，每天 9:25 自动存一份全市场竞价快照。攒够几个月，就能回测完整综合分（而不只是竞价涨幅一个因子）。

### 它是怎么工作的

页面右下角有一个「快照积累」面板：

```
已记录 N 个交易日     ← 攒了多少天
最新：2026-11-20
状态：…               ← 当前在等什么
```

**关键：必须在 9:25–9:30 之间让页面开着。**

原因是竞价成交量 `f5` 只在那个窗口等于竞价量，一开盘就变成全天成交量了。所以：

| 抓取时机 | 竞价涨幅 | 竞价量 | 标记 |
|---|---|---|---|
| 9:25–9:30 自动抓 | 准 | 准 | `q=1` |
| 其他时间手动补抓 | 准 | **不准**（已是全天量） | `q=0` |

补抓也有价值（竞价涨幅始终是准的），但量能类因子不能用。

### 数据存在哪

存在浏览器的 **IndexedDB**（不是 localStorage）。

原因：全市场每天约 5000 条，localStorage 只有 5MB，存两个月就满；IndexedDB 能存几年。

每天约 175KB，一年 250 个交易日约 44MB，IndexedDB 足够。

**注意**：数据在这个浏览器里，换浏览器或清缓存会丢。所以建议定期导出。

### 操作

```
① 交易日 9:20 前打开看板
② 什么都不用做，9:25 它会自己抓
③ 面板显示「已记录 5005 只（含竞价量）」就成功了
④ 点「查看数据」可以看到每天存了什么
⑤ 攒一段时间后点「导出」，得到 auction-snapshots-YYYYMMDD.json
```

### 怎么确认存了什么

点面板上的 **「查看数据」**，会弹出一个明细表：

| 日期 | 抓取时间 | 类型 | 记录条数 | 竞价上涨 | 最高竞价涨幅 |
|---|---|---|---|---|---|
| 2026-11-20 | 09:25:03 | 含竞价量 | 5005 | 812 | 9.87% |
| 2026-11-19 | 11:12:44 | 仅涨幅 | 5005 | 1203 | 8.42% |

「类型」一栏是关键：**含竞价量** 的数据能用于量能因子回测，**仅涨幅** 的只能用竞价涨幅。

**点任意一行可以进入当天的完整明细**，看每只股票的具体数据：

| 代码 | 名称 | 竞价涨幅 | 竞价量(手) | 昨收 | 今开 | 竞价金额(万) |
|---|---|---|---|---|---|---|
| 002086 | 东方海洋 | +4.40% | 98,765 | 5.68 | 5.93 | 5,857 |
| 300812 | 易天股份 | 0.00% | 211,456 | 15.00 | 15.00 | 31,718 |

明细默认按竞价涨幅降序，一次显示 200 条，「显示更多」继续加载；勾上「只看竞价上涨」可以过滤掉低开的股票。

竞价金额是按 `竞价量 × 100 × 今开` 估算的（集合竞价成交价就是开盘价），单位万元。

导出的 JSON 结构：

```json
{
  "v": 1,
  "exported_at": "2026-11-20T03:30:00.000Z",
  "days": [
    { "date": "2026-11-20", "t": "09:25:03", "q": 1, "n": 5005,
      "rows": [["300812", 0, 211456, 15.0, 15.0], ...] }
  ]
}
```

`rows` 每行是：`[代码, 名称, 竞价涨幅%, 竞价量(手), 昨收, 今开]`。

（早期版本存的是 5 个元素、没有名称，读取时会自动兼容，名称显示为 `—`。）

面板上的「立即抓取」可以手动补当天，「清空」要先导出备份。

### 攒多少天够用

没回测过的完整综合分有 5 个因子需要历史数据。粗略的统计要求：

```
30 天   能看方向，但结论不可靠
60 天   可以初步做区间分析
120 天  约半年，够做分组统计和稳定性检验
250 天  一年，能跨一个完整的市场周期
```

**建议至少攒到 120 天再做完整回测**，否则结果会被单一行情主导（现有 500 天样本里就出现过 2026-07 和 2026-10 全线大亏的月份）。

### 一个已知限制

如果某天 9:25 页面没开，那天就永远缺一份带竞价量的数据——接口不提供历史补抓。这是数据源的限制，不是实现问题。

## 七、回测结果（重要）

`backtest/` 目录做了回测：500 个交易日、全市场 5565 只、T+1 可执行口径。

**结论：按现有逻辑（买竞价高开、按竞价涨幅越高越好排序），没有超额收益，而且双重跑输。**

```
前 3 名（竞价涨幅<7%）  日均 -0.098%   超额 -0.155%   跑赢基准 47.0%
前 3 名（不限）         日均 -0.478%   超额 -0.535%   跑赢基准 47.6%
全市场等权基准          日均 +0.166%
```

诊断出的根本原因：**「只买竞价上涨的股票」这个筛选条件本身就比全市场差 0.1%/天**，再按竞价涨幅排序又损失 0.16%/天。

而真实的规律是**倒 U 型**，不是单调递增：

```
竞价涨幅 2~3%   日均 +0.337%   ← 峰值
竞价涨幅 7~10%  日均 -0.878%   ← 悬崖，25 个月里 17 个月亏
```

**原策略把最高分给了最差的区间**——方向刚好相反。

完整证据、局限与复现命令见 [backtest/README.md](backtest/README.md)。

**这个结论的边界**：只验证了「竞价涨幅」一个因子（权重 0.32），因为其余因子（竞价量、量比、警示类型）没有历史数据可重建，「今日涨幅」在 9:25 时尚未产生。**所以这不是对完整综合分的判决，但它足以说明核心排序方向是错的。**

## 八、没做的事（明确边界）

- **没有加止损/仓位/风控。** 它只是排序工具。
- **「9:30 锁定」仍然只是 UI 层面的。** 刷新页面就能重新选股，因为 `isDataCachedBot` 是内存变量。真要硬锁得持久化，原版就没做，我也没加。
- **没解决数据源风险。** 内部接口随时可能变。
- **没有按回测结论改评分函数。** 回测发现「倒 U 型」才对，但改它等于重写策略，属于产品决策，不在「修 bug」范围内。要改请明确要求。

## 九、这是分析工具，不是投资建议

代码修的是「算得对不对」，不是「该不该买」。回测给出的是统计事实，不是收益承诺。任何策略在实盘前都要独立验证，并计入交易成本与冲击成本。
